## Continuation Update: The Architecture Changed

The 2026-08-28 handover correctly described the project at the boundary between commissioning scripts and a physical `ros2_control` backend. That direction was reconsidered because the Raspberry Pi runs Debian 13 (`trixie`, `arm64`), does not have ROS installed, and Orion does not currently need ROS discovery, distributed nodes, or the wider ROS ecosystem to perform its core behaviours.

The project now uses a ROS-independent architecture:

- `runtime/` is the native C++ hardware daemon and STS3215 driver.
- `motion/` is the shared pose, motion, limit, and portable Python validation layer.
- `description/` owns the neutral URDF and the single canonical mesh set.
- `simulation/mujoco/` contains only MuJoCo-specific model and tooling code and consumes shared project assets.
- `hardware/servo_setup/` remains the Python commissioning/calibration toolkit, not the permanent motion controller.

The complete `ros2_ws/` and remaining ROS-specific nodes, launch files, controller metadata, and packages were removed in commit `e817682`. Useful architecture history was retained under `docs/archived/ros2/`.

This is not merely a directory cleanup. The working physical control path is now `oriond`, built with ordinary CMake and no ROS installation.

## What Was Worked On

### Servo audit and LeLamp-compatible configuration

The read-only verification command was extended and its output simplified. It now exposes live state plus the persistent and runtime registers needed to compare Orion with the LeLamp setup without moving or energising a servo.

The five detected servos remain FEETECH STS3215 units reporting model `777`, firmware `3.10`, and approximately `6.2 V`. The native driver applies only intended profile differences while torque is off:

- position operating mode `0`
- return delay `0`
- phase bit `0x10` cleared while preserving unrelated phase bits
- `P=16`, `I=0`, `D=32`, with an Orion-specific elbow `P=32` override
- maximum and runtime acceleration `254`

It deliberately does not lower or rewrite:

- persistent `Max_Torque_Limit`
- runtime `Torque_Limit`
- `Goal_Velocity`
- protection current
- temperature limit

The driver's configuration, activation, wrap conversion, profile-difference, torque-on refusal, and fault refusal paths are covered by fake-transport C++ tests.

### Native C++ hardware runtime

`runtime/build/oriond` now owns the servo bus and maintains a 50 Hz daemon loop over `/tmp/oriond.sock`.

Supported operations are:

- `--check`: one read-only synchronized hardware snapshot, then exit
- `--serve`: start the persistent torque-off observer
- `--status`: fetch the current versioned JSON snapshot
- `--configure`: apply and verify only required servo-profile changes with torque off
- `--enable`: seed measured positions as goals, verify them, then enable holding torque
- `--goto POSE --duration SECONDS`: execute one complete named pose with a quintic trajectory
- `--play MOTION`: execute a validated multi-keyframe YAML motion
- `--stop`: stop active movement at the latest commanded position and keep holding torque
- `--disable`: cancel motion if necessary and turn torque off

The daemon lifecycle is explicit: `observe -> configured -> holding -> moving -> holding`. All five targets are validated against physical calibration before a trajectory begins, and each 50 Hz update uses synchronized position writes.

Torque-off settling can leave a servo a few raw steps outside an inset command bound. The trajectory builder now clamps only its starting command to the nearest safe boundary and moves inward. It does not widen calibration or silently alter the requested destination.

Motion playback is asynchronous. The command returns when playback is accepted, not when the last keyframe finishes. A caller must poll status or wait for at least the reported duration before issuing another move. Calling `--stop` after a motion has already completed correctly reports `no movement is active`.

There is one known UX defect: a `goto` sent while a previous motion is still active can return `enable holding torque before moving`, although torque remains enabled and the real condition is “motion already active.” Fix the error message and add a wait-capable client path rather than extending shell sleeps.

## Key Decisions & Why

### Native C++ is Orion's production control path

The motion loop, serial ownership, lifecycle, and fault boundary belong in C++. Python remains appropriate for calibration tools, validation, simulation authoring, and future high-level behaviour clients. This gives the Pi a small deterministic runtime without forcing a ROS installation that Orion does not currently use.

### Physical calibration defines the coordinate system

The robot's accepted neutral and safe travel are authoritative. MuJoCo and pose files adapt to those values. Recalibrating physical zero requires resynchronising the tracked simulator calibration and reviewing every authored pose; it must not be treated as a cosmetic change.

### Calibration bounds remain mandatory

Removing arbitrary velocity/torque ceilings did not mean removing position safety. The native runtime ignores the old simulation-only dynamic ceilings, but every commanded pose/keyframe must still fit the accepted physical range. Supported endpoints are narrow, documented exceptions rather than globally expanded limits.

### Rest is captured on hardware

Gravity, real cable routing, friction, and mechanical contact determine the actual torque-free rest. It is captured on the assembled robot, checked for stability, saved to the shared library, and then visualised in MuJoCo.

### Shared assets live above all backends

Poses, motions, limits, meshes, and the neutral robot description are product data. Neither C++, MuJoCo, nor a future ROS adapter should own them. Each backend consumes the same definitions.

### Keep daemon execution non-blocking, add client-side waiting

The 50 Hz daemon must continue telemetry and accept stop/disable commands during motion. The user-facing CLI or a sequence client should offer `--wait`/status-aware completion so demo scripts do not guess with `sleep`.

## Lessons Learned & Gotchas

- Rated servo torque is not a command ceiling and does not guarantee continuous operation at stall; structure, leverage, voltage sag, current, heat, and control tuning still matter.
- The corrected head mass is about 120 g excluding servos. Do not reuse the earlier 291–300 g estimate in torque models.
- The elbow holds the upper arm/head load and is the most mechanically demanding joint. Its present higher `P=32` override is intentional; do not copy it blindly to every joint.
- A successful command response means accepted, not completed. Use the returned duration and status state.
- A motion ending naturally leaves Orion holding the final pose. `--stop` is only meaningful while motion is active.
- `--disable` during motion immediately removes torque. Prefer reaching `rest` first whenever feedback and the path remain safe.
- If an obstacle prevents rest, the current daemon has no tracking-fault or collision response. Stop/disable decisions require observation; this is the next major safety gap.
- The live calibration is outside Git on the Pi. The tracked simulator copy can silently become stale after recalibration unless its hash is checked and deliberately updated.
- The shoulder and elbow supported-rest bounds have no extra margin. They are accepted mechanical endpoints, not extra travel to command through.
- Do not reintroduce one-off Python pose scripts as a second production controller. Diagnostics should use the commissioning tools; normal movement should use `oriond`.
- Do not restore ROS merely to gain sequencing. A small native behaviour layer is sufficient for the current robot and does not prevent a future ROS adapter.

## Gotchas for Next Agent

- Read this report, `runtime/README.md`, `hardware/servo_setup/README.md`, and `docs/Orion Guidebook.md` before modifying control behaviour.
- Use the Pi calibration file as truth; the simulation copy is a deliberate mirror, not the authority.
- Keep the daemon running in one terminal before sending `--configure`, `--enable`, `--goto`, or `--play` from another.
- Wait for asynchronous movement to finish. The returned `duration_seconds` is currently the minimum safe wait hint; status polling is better.
- Go to `rest` before normal torque disable. Do not assume `home` is safe when unpowered.
- Never command beyond the calibrated position bounds, including from MuJoCo-authored poses.
- Do not add another torque or velocity ceiling merely to mask motion problems. Diagnose mechanics, supply voltage, tracking, current, temperature, and duration separately.
- Do not delete the Pi stash or live calibration while cleaning Git state.
- Do not expect ROS commands or packages; active ROS code was intentionally removed.
- The known “enable holding torque” error during an already active motion is misleading and should be corrected early.
